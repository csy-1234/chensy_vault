# 软件架构

 [[常见软件架构]]

 C/S架构的客户端形态
 
```
Client / Server（广义）
├── B/S（Browser / Server）
│   └── Web 项目
├── Native C/S
│   ├── 桌面程序
│   ├── 手机 App
│   └── 命令行工具
└── Hybrid C/S
    ├── App + HTTP API
    ├── Electron + Web
    └── 小程序
```

> **这两个 C/S 在“架构本质”上没有区别，  
> 区别只在「客户端技术形态 + 通信方式是否 Web 化」**

它们**不是两种架构**，而是 **同一架构（C/S）的两种实现风格**

Native C/S（传统 / 原生 C/S）
	客户端是**原生程序**
	协议通常是**私有协议或非 HTTP**
     客户端和服务端**强耦合**

特点

|维度|说明|
|---|---|
|客户端|C++ / Java / Swift / Kotlin|
|协议|TCP、私有二进制协议|
|更新|客户端必须升级|
|典型|QQ 早期、银行柜面系统|

👉 **这是“教科书里的 C/S”**

Hybrid C/S（现代混合 C/S）

定义

- 客户端仍然是**专用客户端**
    
- 但通信方式**完全 Web 化（HTTP / JSON）**
    
- 服务端像 Web 一样提供 API
    

 特点

|维度|说明|
|---|---|
|客户端|App / Electron / 小程序|
|协议|HTTP / HTTPS|
|服务端|REST / GraphQL|
|更新|服务端独立演进|

👉 **这是“现实世界里的 C/S”**


## API
是
	一个系统对外暴露的“可被程序调用的功能接口契约”。
	API = 系统能力 + 调用约定（接口）



## 落地设计系统

> [!core]
> 系统 = 客户端形态 × 服务端架构 × 通信方式（可选第三轴

- **客户端形态**：用户“从哪里进来”
- **服务端架构**：系统“内部怎么组织”
- **通信方式**：两者“怎么说话”
它们**彼此独立、可任意组合**。

第一轴：客户端形态（Client Form）
```
客户端形态
├── Browser（Web / B/S）
├── Native App（iOS / Android）
├── Desktop Client（PC 客户端）
├── Mini Program（小程序）
├── CLI / Script
└── IoT / Embedded
```

第二轴：服务端架构（Server Architecture）
```
服务端架构
├── 单体（Monolith）
├── 三层架构（Presentation / Business / Data）
├── SOA
├── 微服务（Microservices）
└── 事件驱动架构（EDA）
```

第三轴 ：通信方式（Communication）
```
通信方式
├── HTTP / HTTPS（REST / GraphQL）
├── RPC（gRPC / Thrift / Dubbo）
├── Message Queue（Kafka / RabbitMQ）
└── Stream / Event（WebSocket / SSE）
```

第四轴:   节点角色组织方式（Topology）
P2P 不是传统意义上的“服务端架构”，  
而是一种「节点组织与角色分布架构」,不是二层轴server architecture，而是“系统拓扑架构”
